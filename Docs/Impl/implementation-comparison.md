# 既存実装との比較・見落としレビュー

調査日：2026-09-24。比較対象：作業ツリーの既存C#実装（HEAD `29eedff`）と [ゼロベース再設計](clean-room-design.md) の初版。

## 1. 結論と調査範囲

初案の「状態遷移を集約する」「書込み結果を確認する」「復元の所有権を記録する」という方向は有効である。ただし、その構成だけではUnity上の安定動作を再現できない。既存実装には、トラッカーの生成時期、Unity自身のロック復元、IMGUIの描画パス、遅延したSelection通知に合わせた対策があり、これらを省くと再実装が退行する。

特に、初案の「ロック状態のポーリングから手動解除を認識する」という方針は修正が必要だった。既存実装は、Unityによるトラッカー再生成時のロック落ちを手動操作と取り違えないため、明示操作と実状態の観測を分けている。この意味を新しい状態モデルにも残す。

既存実装はすでにSelection購読の集約、描画からの状態変更の分離、遅延処理、キャッシュ、保存のまとめ書きを実施している。新設計の改善点は、これらの導入そのものではなく、処理結果・世代・所有権を明示し、失敗や競合時にも同じ規則で扱えるようにすることである。

調査は静的コードレビューであり、Unity実機での動作・性能測定・不具合再現は行っていない。コードのコメントに記載されたUnityの挙動は「その対策を実装した背景」として扱い、すべてのUnityバージョンでの事実と断定しない。変更したのは設計文書のみである。

主な確認範囲：`Core`の反射・イベント・初期化・セッション保存、`Controllers`の回転・履歴・除外・フィルタ・ショートカット、`Services`のInspector・履歴・お気に入り・保存、参照モデル、Managerと一覧・オーバーレイUI。以下ではファイルリンクとメソッド名を根拠として示す。

## 2. 設計と挙動の比較

「初案」は今回の修正前、「改訂」は今回反映した方針を指す。

| 項目 | 既存実装 | 初案との差・改訂後の判断 |
| --- | --- | --- |
| 全体構成 | ServiceLocator、同期EventBus、ControllerとStrategy | 明示DI、Reducer、実行結果付きキューへ変更。ただし既存の責務分割は既に存在する |
| Selection入口 | SelectionCoordinatorから集合とactiveを配信 | 集約は共通。新設計は受付世代、期待通知、通常履歴と回転履歴の処理順を明文化 |
| Inspector更新 | ウィンドウAPI優先、トラッカーAPI代替、再構築・GUI flush・Repaint | 初案で不足。具体的なアダプタ契約として引き継ぐ |
| 代替更新 | 一時アンロック→delayCallで再ロック。サイクル相当 | 新設計は原則不採用。厳密な対象割り当てを保証できなければ回転を停止する |
| 手動解除 | 拡張UI・ショートカットの通知のみ。観測したロック落ちは再ロック | 初案のポーリングによる意図推測を撤回。明示操作と観測を分離 |
| 履歴モード | 最近使った重複なしの選択集合。開始時に履歴と既存表示から補完 | 初案は重複を保持し、初期補完が弱かった。改訂で既存の比較用途を継承 |
| サイクルと戻る・進む | ナビゲーションでは次のInspectorへ進めない | 初案では通常更新扱いだった。改訂で候補を維持 |
| 複数選択フィルタ | 全対象がブロック対象なら停止。混合選択は全体を通す | 初案の「1件でも該当で停止」を撤回。集合を削らず既存の通過条件を継承 |
| 選択履歴 | activeObjectを1件として永続保存 | 新設計は集合＋activeを記録し、当初はセッション内。互換性変更として明記 |
| 選択の同一性 | 回転は配列の順序込み。履歴サービスは単一対象の同一性 | 新設計は集合＋active。順序だけの変更を新しい選択にしない |
| 初期状態・再同期 | 実際のロック対象を読み、履歴とキャッシュを再構築 | 初案の抽象的な再読込処理を補強。明示的な配置予約を優先する |
| 再読込・Play往復 | 実行状態をSessionStateで保持し、遅延してロックを貼り直す | 新設計は配置情報を保持するが回転はOffへ。自動継続しないのは意図的な変更 |
| 途中参加 | 未観測Inspectorをロックして自動参加 | 新設計はManagerで生成・登録した対象だけ参加。外部生成は明示登録 |
| 除外 | ロックして表示を固定し、回転順から外す | 初案の「ロックを変えない」を撤回。表示固定を継承し、Leaseで元値を保護 |
| 終了時のロック | 開始時にロック済みの一覧を保存し、終了時の全Inspectorに適用 | 新設計は参加時点の各Leaseを保存。所有していないInspectorは復元対象にしない |
| 固定番号 | 初観測順を保存し、現在一覧のindex＋1で表示 | 新設計は独立した非再利用番号。既存は途中閉鎖後に番号が詰まるため保証範囲が異なる |
| ドラッグ | Inspector/お気に入りの参照を持ち、遅延実行時に位置を再解決 | 継承。新設計は安定IDと処理世代でも検査する |
| ショートカット | Unity Shortcutを使用。Inspector非フォーカス時は先頭を操作 | 前者は共通。新設計では対象がなければ操作しない |
| 保存 | 固定接頭辞のEditorPrefs＋まとめ書き、SessionState | 新設計はプロジェクトごとの保存、スキーマ・破損復旧・移行を追加 |
| 参照解決 | GUID＋local ID、シーンはInstance ID、キャッシュ | GUID＋local IDとキャッシュは継承。誤った代替解決と再起動後の一時ID使用を防ぐ |
| オーバーレイ・自動フォーカス | 固定番号、ロック操作、次対象、フラッシュ、入力先配慮 | READMEだけでは拾えなかった既存機能。改訂設計で保持対象として追加 |

## 3. 引き継ぐべきUnity固有の対策

### 3.1 未生成トラッカーとロック付き割り当て

根拠：[InspectorReflection.cs](../../Core/InspectorReflection.cs) の`EnsureInitialized`、`GetTracker`、`SetInspectedObjects`。

既存コードは`m_Tracker`の直接読取だけに依存せず、生成を伴う`tracker`プロパティを優先する。また、`InspectorWindow.SetObjectsLocked`を優先し、トラッカー経由では自分で`isLocked`を立てる。初案の「対象に書き込む」という抽象操作だけでは、この違いが抜けていた。

改訂では生成待ちと非対応を分離し、両経路を別々に検証する。`ForceRebuild`、staticなGUI最適化ブロックのflush、`Repaint`まで含めて表示反映の契約とする。メンバーが見つかったことだけを能力保証にはしない。

### 3.2 本当のロック対象を読む

根拠：[InspectorReflection.cs](../../Core/InspectorReflection.cs) の`TryGetLockedObjects`、[RotationLockController.cs](../../Controllers/RotationLockController.cs) の`InitializeRotation`、`ReassertLockStates`、`AssignToInspector`。

既存コードは`activeEditors`をロック対象集合の代用にしない。コンポーネントのEditorも含むためである。開始時も現在のSelectionを全枠のキャッシュにコピーせず、各Inspectorの実表示を読む。元々別対象にロックしていたInspectorを「更新済み」と誤認することを防いでいる。

新設計も同じ読取方式を必要とする。キャッシュは直近に命令した値ではなく、検証済みの実表示を表す。表示名用の代表オブジェクトと、正確な割り当て・復旧用の集合は別APIとする。

### 3.3 ロック落ちと利用者の意図は別

根拠：[RotationLockController.cs](../../Controllers/RotationLockController.cs) の`Reconcile`、`OnInspectorLockChanged`、`SetInspectorLocked`。

既存は`_userUnlocked`へ入れる経路を拡張経由の明示操作に限定し、自身の書込みは`_applyingLock`で抑止する。定期観測で見つけた解除は再生成などによる状態破損として扱う。

初案の「標準Inspectorのロック操作をポーリングして同じ遷移へ変換」は、操作元の区別ができず退行を招く。改訂では手動意図と観測値を分け、操作元が実証できない標準南京錠の操作まで同等に扱うとは約束しない。

### 3.4 Unity自身の復元後に再検証する

根拠：[RotationLockController.cs](../../Controllers/RotationLockController.cs) の`ScheduleReassert`、`OnPlayModeStateChanged`、`ReseedStrategyFromDisplay`、`ScheduleApplyLayout`。

既存はInspectorの`OnEnable`等による復元より後にロックを再設定するためdelayCallを使う。さらに実表示から戦略の履歴を作り直し、履歴消失による同じ内容の重複表示を抑える。`_layoutApplyQueued`で明示的な新配置を復旧処理が上書きしないようにしている。

改訂では遅延を保持しつつ、「1フレーム待てば必ず準備完了」とはせず、期限付き準備確認にする。表示からの復旧より新しい設定リビジョンを優先する。自動回転を止める設計でも、停止前のロック復元が後からUnityに上書きされる可能性は別途扱う。

### 3.5 GUI描画中に処理しない

根拠：[InspectorStatusView.cs](../../UI/InspectorStatusView.cs)、[HistoryListView.cs](../../UI/HistoryListView.cs)、[FavoritesListView.cs](../../UI/FavoritesListView.cs) の遅延変更、[InspectorWindowService.cs](../../Services/InspectorWindowService.cs) の`GetAllInspectors`。

既存は開閉・除外・並び替え・お気に入り変更等を描画後へ遅延し、Layout/Repaintの不一致を防ぐ。Inspector一覧は内部バッファのコピーを返し、再入した列挙で反復対象が変わることも防いでいる。参照を持つドラッグも同じ理由で必要になる。

初案の「直列キュー」だけでは不十分であり、そのキューをGUIコールバック内で同期実行してはならない。改訂では描画外の実行時点、描画スナップショットの寿命、遅延コマンドの世代チェックを追加した。

### 3.6 遅延通知・旧値通知・空選択

根拠：[HistoryService.cs](../../Services/HistoryService.cs) の`NavigateToCurrent`、[RotationLockController.cs](../../Controllers/RotationLockController.cs) の`OnSelectionChanged`、`FlushDeferredSelection`。

既存は戻る・進むの対象を保持し、選択通知が遅れて届いても履歴に再記録しない。回転側は旧選択の重複通知でナビゲーション目印を消費せず、空選択では直前選択を消して再選択を受け付ける。遅延更新中の選択も保留する。

改訂ではこれらを期待通知の照合規則に取り込む。保留は既存の「最後の1件」から有限キューへ変更するが、処理できない入力を黙って失う問題への対策という目的は同じである。

### 3.7 表示再構築・保存・参照解決を毎回行わない

根拠：[RotationLockController.cs](../../Controllers/RotationLockController.cs) の`AssignToInspector`、[EditorPrefsPersistence.cs](../../Services/EditorPrefsPersistence.cs)、[AssetEntryResolver.cs](../../Models/AssetEntryResolver.cs)、[InspectorOverlayController.cs](../../UI/InspectorOverlayController.cs)。

既存は同一割り当ての再構築を省き、約0.5秒間隔の照合、1秒の通常保存待機、アセット解決キャッシュ、終了時刻によるフラッシュ表示を使う。保存待機中でもLoad/HasKeyは最新値を見られる。

改訂ではこの性質を保持する。時間値そのものは実測で決め、キャッシュの無効化条件と保存順序を追加する。新設計が「正しさのため毎フレーム全部読んで全部作り直す」ものにならないようにする。

## 5. 既存実装をそのまま引き継がず強化する箇所

以下はコードの制御経路から分かる問題またはリスクであり、今回実機で発生を再現した不具合一覧ではない。

### 5.1 遅延処理の失効確認

`PerformLegacyUpdate`のdelayCallは`_disposed`を確認するが、有効状態・一時停止・タイムアウト後の処理世代を検査していない。終了処理で元のロックに戻した後でも、遅れて再ロック・順序移動・成功通知を実行する経路がある。`Reconcile`のタイムアウト解除だけでは予約済みコールバックは取り消せない。

新設計では直接更新・UI操作・復旧・任意の代替経路すべてに世代付き操作IDを持たせる。期限切れ処理の結果を捨てるだけでなく、副作用を実行する前に失効を確認する。

### 5.2 失敗結果が成功通知へ流れる

`CycleRotationStrategy.Apply`は`context.Assign`の戻り値を確認せず順序を進めて通知する。`HistoryRotationStrategy.ApplyLayout`も各Assignの結果を集約せず、`Apply`は更新通知を発行する。履歴自体も割り当て成功前に変更される。

また、`GetLockedState`の読取失敗は`false`、`SetLockedState`は例外をログにして戻るため、サービスが失敗を区別できずロック変更イベントを出す可能性がある。

新設計は`Result<T>`等で「解除状態」と「取得失敗」を分け、検証成功後だけ順序・履歴・通知を確定する。既存の例外隔離は残すが、例外を受け止めることと成功判定は分離する。

### 5.3 一時アンロックによるフォールバックの限界

既存の旧方式はUnityの現在Selectionへの追従を利用する。待機中に選択が変わると、通知に渡す元の`newSelection`と実際の表示対象が一致するとは限らない。履歴モードでもサイクル相当となる。

新設計はこの経路を標準機能と同じ保証では提供しない。回転不能時に履歴・お気に入りを継続する方式を既定とする。将来残す場合は、制約を明示した別モードとして、実表示の読戻し・期限・キャンセルを実証する。これは対応環境の幅を狭めうるトレードオフである。

### 5.4 ロック復元の範囲

`RestorePreRotationLockStates`と`SuspendForWindowClose`は現在の全Inspectorを列挙し、開始時ロック済み一覧に含まれるかで復元する。開始後に加わった元々ロック済みのInspectorも、開始時一覧にいなければ解除される構造である。

新設計はウィンドウごとの参加時点でLeaseを取得する。全ウィンドウの現在値から復元を推定しない。途中参加・外部生成・除外・閉鎖を組み合わせたケースを回帰試験にする。

### 5.5 参照失効と永続化

`AssetEntryResolver.ResolveUncached`は、local IDが見つからない場合にメインアセットを返す。シーン用の`HistoryEntry`と`FavoriteEntry`はInstance IDを保存し、再起動後にも解決を試みる。EditorPrefsのキーはプロジェクト識別を含まない。

アセット参照でGUIDを優先しサブアセットを識別する工夫は引き継ぐが、見つからない場合の代替解決は撤回する。永続IDを用意できない項目はセッション限定・所属不明として扱い、別対象を選択しない。未ロード状態を単なる無効として自動削除しない。

### 5.6 コメントと実装の保証範囲

ウィンドウ番号は初観測順で安定化されているが、UIは現在の一覧のindex＋1を使うため、途中のウィンドウを閉じると後続番号が詰まる。「固定番号」を閉鎖後も不変と解釈する場合、新設計の独立番号が必要である。

除外保持についても、`InitializeRotation`は除外を考慮する一方、`IsEnabled=false`の経路では除外一覧をClearする。したがってコメントから「OFF→ONで必ず除外が保持される」とは結論できない。新設計では停止と設定破棄を別操作にする。

`SelectionFilter`もコメントに「個別制御」とあるが、特殊カテゴリを通過しても後続の`BlockDefaultAsset`や`BlockTextAsset`の条件が適用される。新設計の分類はカテゴリの優先順位・包含関係を定義し、各設定の組合せをテストする。

## 6. 意図的に残す互換性変更

次の項目は初案の見落としではなく、改訂後も残す設計判断である。再実装を配布する際には挙動変更として説明する必要がある。

- **再読込・Play境界で自動継続しない**：既存の継続性より安全な再確認を優先する。役割順・除外・固定番号は保持する。検証後に自動継続を追加する場合も、復旧状態機械を通す。
- **外部生成Inspectorを自動参加させない**：意図せずロックを書き換える範囲を限定する。Manager生成のInspectorは自動参加を維持する。
- **不完全な履歴集合を部分表示しない**：既存の`Compact`は生存対象だけへ縮める。新設計は元の集合を維持し、表示候補から項目ごと除外する。
- **通常履歴を集合単位・当初セッション限定にする**：既存の単一activeObjectの永続履歴とは異なる。旧データを削除せず退避する。
- **履歴クリックをカーソル移動とする**：既存UIの直接選択は戻る・進む通知を通さない。新設計は統一する。
- **サイクルの並び替えは同順位の優先順に使う**：既存は回転キュー自体を並び替える。新設計は最古成功順を優先するため、利用者への説明が必要。
- **一括操作の対象を明示登録済みに限定し、非フォーカス時のCtrl+Lは何もしない**：既存は全Inspector対象・先頭への代替操作がある。
- **能力不足では自動回転を止める**：旧アンロック方式への自動切替より、保証可能な機能を継続する。

これらは「新設計の方が常に優れている」という意味ではない。特に再読込後の手動再開と永続履歴の範囲は、既存利用者の操作負担に影響する。安定化対策の移植と、これらの機能仕様変更を同じ変更として扱わない。

## 7. 実装前に確認するゲート

1. 新規・非表示・ドッキング済みInspectorで、ウィンドウAPI／トラッカーAPIの割り当て、正確な集合読取、空表示への復元を確認する。
2. トラッカー再生成、Inspector自身の遅延復元、標準南京錠操作の観測可能範囲を確認する。操作元が識別できない前提でも安全に動くことを要求する。
3. Assembly reload、Play往復、Domain Reload無効時に、停止・復元・準備待ち・配置保持が矛盾しないことを確認する。
4. 待機中のOFF・Pause・閉鎖・モード変更・タイムアウト後に古い処理が書き込まないことを障害注入で確認する。
5. 戻る・進む、空選択、混合選択、開始時の履歴補完、GUI描画中の操作について既存の安定化シナリオを回帰試験化する。
6. サブアセット、シーン未ロード、ID再利用、旧保存データの移行で参照を取り違えないことを確認する。

これらを通過してからReducer・キュー中心の構成へ接続する。Unity操作の成立を未確認のまま抽象構造だけを完成させない。
