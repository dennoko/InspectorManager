# Inspector Manager ゼロベース再設計

## 1. 目的と設計の前提

本書の初版は [README.md](../../README.md) の機能・利用目的を要件として、既存実装を参照せずに設計した新規実装案である。その後、2026-09-24に既存実装を静的に調査し、Unity固有の安定化対策を反映した。比較結果と初版からの変更理由は [既存実装との比較・見落としレビュー](implementation-comparison.md) に記載する。READMEのアーキテクチャ欄は制約とせず、構成はゼロベースの案を維持する。

目的は、複数のUnity標準Inspectorへ現在と過去の選択を割り当て、比較・編集のための操作負担を減らすこと。そのために「選択を正確に表示する」「利用者のロック状態を壊さない」「Unityの再読込や内部APIの変更で暴走しない」を優先する。

対象環境はREADMEにあるUnity 2022.3.22f1、.NET Standard 2.0。Unity内部APIの具体的なメンバー名や実際の挙動は本書では検証済みとしない。後述する実証段階で、対象Editor実機上で成立を確認してから採用する。他のUnityバージョンは、動くと推測するだけでは対応済みとしない。

以降の「採用仕様」はREADMEが明記していない境界条件についての提案であり、既存の動作を表すものではない。

## 2. 要件と受け入れ条件

| READMEの要件 | 新設計で保証する動作 |
| --- | --- |
| 履歴モード（既定） | 参加Inspectorの役割順に、最新・1つ前・2つ前の選択集合を割り当てる。番号は並び替えで変わらない |
| サイクルモード | 更新成功が最も古い参加Inspectorを1つ更新する。同順位でも選択結果が決定的になる |
| 複数選択 | 選択集合を欠落させずUnity標準Inspectorへ渡す。アクティブ対象はモデルで保持し、Inspector内での再現能力は別途検証する |
| Inspector追加・削除・並び替え・除外 | 対象を一意に識別し、役割順とウィンドウ識別を分離する |
| 個別・一括ロック、Ctrl+L | 同じコマンド処理を経由する。手動解除でローテーションを離脱し、再ロックで復帰する |
| 終了時のロック復元 | 生存する同一Inspectorに、その管理セッションの開始前の状態を復元する |
| 一時停止・再開 | 停止中は管理対象の表示を維持し、再開後の処理を決定的にする |
| 履歴・戻る・進む・ドラッグ | 履歴移動による選択を通常の新規選択と区別し、循環や重複追加を防ぐ |
| お気に入り・再起動後の保持 | プロジェクト単位で保存し、対象が解決不能でも登録情報を失わない |
| カテゴリ別更新ブロック | 選択そのものを変更せず、Inspectorへの割り当てだけを抑止する |
| 内部API非互換時のフォールバック | 変更可能な機能を限定し、復元可能なロックを復元して自動更新を停止する |

非目標は、独自InspectorでUnity標準編集を再実装すること、シーンやアセットの内容を変更すること、任意のUnityバージョンへ推測で対応すること。履歴からの選択と明示的な戻る・進む以外では、グローバルSelectionを書き換えない。

## 3. 採用する構成

```text
Manager UI / Shortcut
          │ Command
Unity events → Event ingress → 単一の処理キュー
                                  │
                         State reducer（純粋関数）
                                  │
                             Effect plan
                                  │
                         Main-thread executor
                           │              │
                    Unity adapter     Persistence
                           │              │
                           └─ 結果をキューへ ─┘
                                  │
                         確定状態 → UI snapshot
```

- **Domain**：選択集合、履歴、参加条件、割り当て、状態遷移を扱う。Unity API、時刻、ファイル、UIへの依存を持たない。
- **Application**：コマンドの直列化、処理世代、計画作成、成功結果の反映、失敗からの復旧を担う。
- **Unity adapter**：Inspector列挙・識別・ロック・表示対象の読書き、Selection、オブジェクト解決を隠蔽する。内部APIの利用はここに閉じ込める。
- **Persistence**：設定・お気に入り・復旧記録を用途ごとに保存する。
- **Presentation**：確定状態の読み取りとコマンド発行のみを行う。描画イベントから購読登録、Selection変更、保存、Inspector更新を実行しない。

起動時にComposition Rootが依存関係を明示的に組み立てる。グローバルService Locatorや、任意の箇所から状態を書き換えられる汎用Event Busは設けない。Unityイベントの購読者はランタイムの入口に集約し、UIを複数開いてもランタイムを増やさない。

## 4. 状態モデルと不変条件

### 4.1 データモデル

| データ | 主な内容・役割 |
| --- | --- |
| RuntimeState | `Off / Starting / Running / Paused / Suspended / Stopping / Faulted`、処理世代、設定、直近の失敗 |
| WindowRecord | セッション内のWindowKey、固定表示番号、役割順、実体への参照、参加状態、最終成功シーケンス |
| LockLease | 同一実体の識別証拠、取得時のロック値、ツールが最後に書いた値、復元進捗 |
| SelectionSnapshot | 順序付きの対象参照、アクティブ対象、比較用キー、受付シーケンス、イベント発生元 |
| NavigationHistory | 通常選択の記録と戻る・進むのカーソル |
| RotationHistory | フィルタを通過し、割り当てを成功させた選択の重複なし最近使用順。初期配置・復旧時は観測済み表示を明示的に種として受け取る |
| FavoriteEntry | 独自ID、永続参照、表示名のキャッシュ、並び順、解決状態 |

WindowKeyは同一セッション内の識別子とし、Unityの一時的なInstance IDを再起動後の同一性判定に使わない。固定表示番号はそのセッション内で再利用せず、役割順から独立させる。再起動をまたぐ番号維持は保証しない。

選択の比較キーは「重複を除いた対象集合＋アクティブ対象」。列挙順だけの変化は新しい選択としないが、表示用には元の順序を保持する。同一集合でアクティブ対象が変わった場合は新しい選択として扱う。

### 4.2 常に守る条件

1. Unity API操作はすべてEditorのメインスレッドで行い、同時に実行する更新計画は1つだけとする。
2. 回転への参加には、生存確認・必要なAPI能力・ロックの取得成功が必要。除外中・手動解除中・故障隔離中のInspectorには割り当てない。
3. 復元元は最初の管理開始時に一度だけ取得する。更新・一時停止・並び替えで上書きしない。
4. UI表示、最終更新順序、RotationHistoryは実行成功を確認してから確定する。
5. 古い世代の遅延処理は何も変更せず破棄する。
6. ロック復元や停止処理は複数回呼ばれても同じ結果になる。
7. 対象参照が解決不能なら、その事実を表示する。別の似た名前のオブジェクトへ置き換えない。
8. 同じ選択、同じ状態、同じ実行結果からは同じ次状態を得る。

## 5. 選択イベントと表示更新

### 5.1 処理手順

1. Selectionイベント受信時に選択集合を即座にスナップショット化し、受付順序と世代を付与する。後からグローバルSelectionを読み直して過去のイベントを再現しない。
2. 明示的な履歴移動によるイベントか、通常選択かを識別し、完全に同一な連続イベントだけを重複除去する。
3. NavigationHistoryを更新する。空選択は履歴に追加せず、現在の割り当ても維持する。ただし受付側の直前選択キーは空に更新し、`A → 空 → A`の再選択を重複通知として捨てない。
4. 実行時に対象の生存・フィルタ・実行状態を再確認し、現在のWindowRecordから更新計画を作る。
5. 書き込み前に、触れる全Inspectorの表示対象とロックを読み、復元可能性を確認する。
6. 計画を実行し、ロック対象集合とロック状態の読戻しで成否を確認する。描画の完了とモデルの更新を同一視しない。アクティブ対象の読戻しを保証できないアダプタは、その能力を別途報告する（第14節）。
7. 全操作成功なら、割り当て、RotationHistory、成功シーケンスをまとめて確定する。失敗時は第8節の手順へ進む。

単なるデバウンスで異なる選択を捨てると履歴の意味が変わるため、通常は選択順序を維持する。1回のEditor更新で処理する計画数に予算を設け、キューには上限を設ける。上限超過時は自動回転を停止し、未処理履歴が欠落した旨を表示する。無限にメモリを増やしたり、黙って最新版だけに置き換えたりしない。

### 5.2 再入・競合の抑止

単一の`isUpdating`フラグだけでは、遅延して届く通知を識別できない。履歴選択の書き込みには「操作ID・期待する比較キー・世代・有効期限」を持つ短命の期待通知を登録する。Selectionの通知に操作IDが付かない場合は、期待キーと実際の観測を照合する。異なるキーは利用者の操作として処理し、待機状態を解除する。

通知が来ない場合も期限付きの読戻しで確定させ、待ち続けない。期待通知の照合前に「前回値の重複通知」を除去し、その通知では期待値を消費しない。同一値の外部操作とは完全には区別できないため、その場合に新規履歴を追加しない仕様とする。Inspectorの更新にはグローバルSelectionの一時的な切り替えを使わない。

対象ウィンドウの閉鎖、除外、モード変更などは計画を無効にする。実行直前に世代・対象集合の版を検証し、古い計画を再利用しない。

### 5.3 履歴モード

参加Inspectorを役割順に並べ、今回の候補選択を先頭へ追加したRotationHistoryから順に割り当てる。例として、役割順が`#3, #1, #2`、履歴が`C, B, A`なら`#3=C, #1=B, #2=A`となる。

RotationHistoryは既存実装の比較用途を引き継ぎ、同じ選択を先頭へ移し、後方の重複を除去する。`A → B → A`の操作列はNavigationHistoryに残すが、表示候補は`A, B`とする。「1つ前」は異なる選択の最近使用順を意味するとUIに明示する。

開始・履歴モードへの切替時は、現在選択、記録済みの有効な選択履歴、実際のInspector表示の順で候補を集める。すべてに現フィルタと完全参照解決を適用し、同一選択だけを重複除去する。集合の一部が重なるだけでは捨てない。既存表示から補った項目は「開始時表示」と区別する。履歴が不足する枠は現在の表示を維持し、「履歴未割当」と表示する。履歴数の上限はInspector数以上とする。

無効な選択集合はRotationHistoryの割り当て候補から集合ごと除き、後続の有効項目を詰める。複数選択を部分集合に縮めない。詰めても不足する枠の旧表示には「履歴未割当」を付け、最新順の表示だと誤認させない。

並び替え・参加復帰・モード切り替え時は、Runningなら現在の履歴を再割り当てする。Paused中は状態だけを変更して、再開まで書き込まない。

### 5.4 サイクルモード

参加Inspectorのうち最終成功シーケンスが最小のものを選び、同順位なら役割順で決める。新規参加枠は未更新として優先する。壁時計を使わないため、時計補正や同時刻によって順番が揺れない。

通常選択の成功時だけシーケンスを進める。戻る・進むでは既存実装と同様に現在の更新候補の表示だけを変更し、更新候補を進めない。並び替えは過去の成功順を消さず、同順位の優先順だけに影響する。履歴モードから切り替える際は全枠を同順位として開始する。モード間で更新順の意味を引き継がない。

### 5.5 ブロックと複数選択

既存実装を引き継ぎ、有効な対象すべてがブロック対象の場合だけ割り当てを抑止する。1つでも許可対象があれば、ブロック対象も含めた元の集合全体を渡す。これによりフォルダとGameObjectの混合選択を受け付け、選択集合の一致も保つ。カテゴリ判定失敗は通常のブロックとは分け、更新抑止として理由を表示する。

NavigationHistoryには記録するが、RotationHistoryと更新順は進めない。ブロック・一時停止は管理下のInspectorに適用する。手動解除済み・管理外のアンロックされたInspectorはUnity本来の選択追従を行うため、そこまで停止できるとは表示しない。除外してロックを維持しているInspectorは表示を固定する。

## 6. ロックとウィンドウ管理

### 6.1 ロックの所有権

回転開始時に、管理する各Inspectorの元のロック状態をLockLeaseとして記録し、ロックしてから参加させる。途中で追加したInspectorでは、そのInspectorを管理し始める直前の状態を保存する。

「明示的な除外」と「手動解除による一時離脱」は別の理由として保持する。再ロックは手動解除の理由だけを除去し、明示的な除外を解除しない。明示除外は既存実装と同様に表示を固定する操作とし、Leaseを取得したうえでロックして、回転への割り当てを止める。除外後に明示的に解除する場合は選択追従を許可するが、除外の理由は残す。

回転中の手動ロック操作はそのセッション内の指定として扱う。終了時にはREADMEの要件に従って開始前の値へ戻す。一方、回転がOffのときのロック操作は通常の手動設定であり、後から勝手に元へ戻さない。回転の停止で明示除外・役割順・固定番号まで消去せず、それらのリセットは別操作とする。

一括操作の対象はManagerに登録された生存Inspectorとし、UIに対象数を表示する。回転中の一括解除は全対象を手動離脱、一括ロックは手動離脱を解除する。明示除外は維持する。元の復元値はどちらでも書き換えない。

手動離脱はManager・オーバーレイ・ショートカットからの明示的コマンドで決める。ツール自身の書込みは発生元を区別する。ポーリングで見つけたアンロックだけから利用者の意図を推測しない。既存実装では、トラッカー再生成によるロック落ちを手動解除と誤認しないため、この区別を設けている。

管理参加中に原因不明のロック落ちを検出した場合は、通常の割り当てを保留し、キャッシュを無効化して、最後の確定割り当てとロックを再検証・再設定する。標準Inspectorの南京錠を手動離脱として認識するのは、操作元を確実に識別できる経路が実証できた場合だけとする。それまでは管理中の手動解除にManager等の操作を案内する。原因不明の解除は回復対象であり、標準UIでの手動操作と完全に両立する保証はしない。

### 6.2 開閉と識別

- Managerから追加する場合：ウィンドウ生成、識別、元状態の記録、必要なロック、登録の順に行う。Running/Paused中は自動参加する。Off中は次回開始時の参加対象になる。
- 生成後に登録が失敗した場合：生成物が空の新規Inspectorで同一実体だと確認できる場合だけ後始末する。不明な場合は閉じずに失敗を表示する。
- 外部で開いたInspector：一覧に検出して表示するが、自動でロックを書き換えず、明示登録後に管理する。
- ManagerからInspectorを閉じる場合：同一実体を再確認し、そのLeaseの元状態を復元してから閉じる。復元失敗時は自動で閉じず、再試行できる状態にする。
- 標準操作で既に閉じられた場合：消失した実体への復元は不可能なので、登録とLeaseを終了する。別ウィンドウを代わりに復元したり、新規生成したりしない。
- 最後のManagerウィンドウを閉じる場合：回転を終了し、生存するInspectorを復元する。非表示の常駐回転は行わない。

### 6.3 状態遷移

| 現在状態・イベント | 遷移と処理 |
| --- | --- |
| Off → 開始 | Startingで能力確認とLease取得。全対象の取得成功後だけRunningへ |
| Starting → 一部失敗 | 取得済みLeaseを復元。復元完了ならOff、不完了ならFaulted |
| Running → 一時停止 | Pausedへ。キューの古い割り当てを破棄し、現表示とロックを維持 |
| Paused → 選択 | NavigationHistoryのみ記録。RotationHistoryには追加しない |
| Paused → 再開 | Runningへ。現在選択を1回だけ評価し、停止中の全選択を連続再生しない |
| Running/Paused → 対象0件 | セッションは維持するが更新しない。UIに対象なしを表示 |
| Running/Paused → 終了 | Stoppingで新規更新を止め、全Leaseを復元してOffへ |
| 実行中 → 更新失敗 | 自動更新を止めて補償処理。結果に応じOffまたはFaultedへ |
| 実行中 → コンパイル・再読込・Play境界 | Suspendedで世代を更新し、可能な間にLeaseを復元する |
| Faulted → 再試行 | 残った復元だけを再試行。自動的にRunningへ戻らない |

一時停止と手動解除が同時に指定された場合は、明示的な手動解除が優先し、そのInspectorは停止保証の対象外となる。

## 7. 履歴とお気に入り

NavigationHistoryとRotationHistoryは目的が異なるため分ける。戻る・進むはカーソルを動かしてSelectionを変更し、新規NavigationHistoryを追加しない。その選択がフィルタを通れば、履歴モードは重複なし最近使用順へ反映し、サイクルモードは候補を進めず表示だけ変更する。

戻った後に別の通常選択を行うと進む側の履歴を破棄する。履歴項目の直接クリックも同じカーソル移動として扱う。処理の途中で対象が消失した場合は選択を変更せず、理由を表示する。

複数選択の一部だけが消失した履歴は、勝手に部分集合へ縮めず選択不能にする。ドラッグ開始時も全参照を解決し、欠落があればドラッグを開始しない。これにより、見えている履歴と実際の編集・ドラッグ対象を一致させる。

お気に入りはプロジェクトに対応する永続オブジェクト識別子を保存する。アセット移動・改名で壊れない参照方式を選び、シーン対象にはシーンとローカル対象の識別を含める。具体的なUnity APIで安定参照できる範囲は実機で検証する。

未保存シーンや一時オブジェクトには、再起動後の復元を約束しない。一時登録として明示し、保存後に同一対象と確認できた場合のみ永続参照へ昇格する。解決のためにシーンを自動で開いたり、アセットを変更したりしない。

未ロード・削除・解決失敗を区別し、未解決お気に入りは名前のキャッシュ付きで残す。削除は利用者の操作で行う。お気に入りの並び順は対象のInstance IDではなくFavoriteEntryの独自IDで管理する。

## 8. Unity内部APIと障害時の動作

### 8.1 能力単位のアダプタ

アダプタは少なくとも「列挙と識別」「ロック読取」「ロック書込」「表示対象読取」「選択集合の割り当て」「生成」「閉鎖」の能力を別々に報告する。型が存在するだけでは成功扱いにせず、引数・戻り値・対象インスタンスとの整合を確認する。

内部APIの検索は初期化時に行い、描画や選択ごとに反射探索しない。起動時の検査は読取中心とし、既存Inspectorを書き換える自己診断は行わない。書込み能力は、対応環境の隔離された検証用Inspectorを用いた事前テストで確かめる。

能力が不足する場合に、名前の似たメンバーを手当たり次第に呼ばない。単一選択しか扱えないAPIへ複数選択を縮めることもしない。回転に必要な能力が欠ければ回転を無効にし、履歴・お気に入りなど独立して動く機能は継続する。

### 8.2 複数Inspectorの更新失敗

Unityのウィンドウ操作には一般的なデータベーストランザクションがないため、完全な原子性は保証しない。複数枠の更新途中が一瞬見える可能性も残る。代わりに、事前状態の記録と補償処理で不整合を限定する。

1. 書込み対象すべての事前表示・ロックを読めなければ、その計画は実行しない。
2. 書込み途中の例外・不一致で直ちに後続処理を止める。
3. 書き換えた生存Inspectorを、逆順で直前の表示・ロックへ戻す。
4. 計画の成功状態は確定せず、自動回転を停止する。
5. 全Leaseの開始前ロックへ復元を試み、終了処理を行う。
6. 補償失敗は対象単位で残す。実表示を再観測し、「復元未完了」を表示する。

「直前の表示へ戻す補償」と「セッション開始前のロックへ戻す終了処理」は別の責務である。通常終了では表示対象まで開始前へ戻すことは要求しない。

能力喪失によって復元自体ができない場合は、完全復元を装わない。自動更新を停止し、対象Inspectorと未完了操作を示す。無制限リトライは行わず、利用者の再試行または再初期化まで待つ。例外を黙殺して通常運転を続けるフォールバックは採用しない。

## 9. 再読込・Play Mode・終了への耐性

実行中の状態をそのままシリアライズして自動再開する設計は避ける。設定とお気に入りの復元、ロックの復旧、回転の開始は分離する。

- **Assembly reload前**：入力受付を止め、世代を更新し、復旧記録を保存してLeaseを復元する。イベント購読を解除する。
- **Assembly reload後**：ランタイムを1つだけ作り、能力検査と未完了復旧を行う。回転はOffから利用者が再開する。
- **Play Modeへの移行・復帰**：同じ停止・復元手順を実行し、Edit Modeの参照をPlay Modeの対象に流用しない。復帰後も自動回転を開始しない。
- **Domain Reload無効**：静的状態が残る前提で購読世代を検査し、二重購読・前回キューの持ち越しを防ぐ。
- **シーンの開閉・アセット削除・Undo/Redo**：参照解決を無効化して再検証する。古い参照を無条件に使わない。
- **Editor終了**：保存とLease復元を試みる。強制終了時の実行は保証できないため、次回起動用の未完了記録を残す。

再読込をまたいで同じInspectorだと証明できるかは、最初に検証すべき技術的条件とする。証明できない場合は自動復元しない。Editor再起動後に一時IDが同じというだけでロックを書き換えることは禁止する。復旧対象が特定できない場合は説明を表示し、手動確認へ誘導する。

既存実装のSessionStateによる役割順・除外・手動解除の保持は引き継ぐ。安全停止しても配置設定と固定番号まで消さない。再読込時の同一性確認には、同じEditorセッション内の記録と、現在列挙できるInspectorの型・ID・生存確認を組み合わせる。再読込後すぐの列挙不足を閉鎖と断定せず、期限付きで準備完了を待つ。Offへ移行することとウィンドウが閉じられたことを混同しない。

`OnDisable`だけを利用者による閉鎖と判定しない。再読込・Play境界・最後のManagerの閉鎖・Editor終了をライフサイクル入口で区別し、停止理由を引き継ぐ。初期化直後の1回の読取りを確定値にせず、Inspector自身の復元後に再検証する。元のロックを戻した後でUnity側の復元に上書きされる場合も検出する。自動回転を再開しない方針は、既存実装からの意図的な互換性変更として維持する。

## 10. 永続化

| 保存対象 | 範囲・保存先の方針 | 復元方針 |
| --- | --- | --- |
| 設定・お気に入り | プロジェクトごとの利用者用領域。プロジェクトに生成アセットを置かない | スキーマ版を検証して読み込む |
| NavigationHistory | 当初はEditorセッション内のみ。有限件数 | 再起動で消去する仕様を明示 |
| RotationHistory・更新順 | 管理セッション内のみ | 終了時に破棄 |
| ロック復旧記録 | Editorセッションと管理セッションを識別する専用記録 | 同一実体を確認できた対象だけ復旧 |

設定・お気に入りはDTOとして保存し、Unityオブジェクトやサービス自体をシリアライズしない。保存先はプロジェクト識別を含み、他プロジェクトのデータを混ぜない。ユーザー間共有は初期仕様に含めない。

永続ファイルはスキーマ版、データ本体、検証情報を持つ。一時ファイルへ書き、読取検証後に同一ファイルシステム上で置換する。直前の正常版をバックアップする。保存処理は直列化し、遅い古い保存が新しい状態を上書きしないようリビジョンで管理する。

読取失敗では正常バックアップを試し、両方失敗なら破損データを退避したうえで既定値を使用する。未知の新しいスキーマは勝手に既定値で上書きせず、保存を止めて通知する。移行処理は元データを残して実行する。

通常設定は変更をまとめて保存できるが、ロックの復旧元は書込み前に記録する。復旧記録の保存失敗時は新しいLeaseを取得しない。書込み成功・復元成功の進捗を更新し、途中終了後にも未完了操作を識別する。強制終了時にUnityレイアウト保存と記録を原子的に揃えることまでは保証しない。

## 11. UI・性能・診断

一覧には、固定番号、役割、参加・除外理由、実ロック状態、割り当て対象、未解決・失敗状態を表示する。コマンド受付と操作成功を区別し、成功していないロックを成功アイコンで表示しない。

Ctrl+LはUnityのショートカット機構へ登録し、Manager内ボタンと同じコマンドへ変換する。実行時にフォーカス中のInspectorを解決し、対象がなければ何もしない。キー入力を独自に横取りしない。設定変更はUnity側の割り当てを尊重する。

Inspector列挙・参照解決はキャッシュし、ウィンドウ変化や関連イベントで無効化する。全体照合は低頻度で行い、毎フレームの全アセット検索や全シーン走査を避ける。UI再描画は表示状態が変化した場合にまとめ、履歴件数を制限する。

ログには操作ID、世代、WindowKey、機能能力、遷移、失敗段階を含める。個々の同一例外はまとめ、毎フレーム出力しない。診断表示から、現在の能力と未完了復元を確認できるようにする。

性能は「選択受付から割り当て確定までの遅延」「計画実行時間」「キュー長」「割り当て回数」「割当メモリ」を測定する。独自Inspectorの描画負荷もあるため、未測定のミリ秒保証は置かない。対象環境でInspector数・選択数・履歴数を増やした基準データを取り、回帰を判定する。

## 12. 検証計画

### 12.1 純粋ロジックの検証

- 履歴モードの役割割り当て、固定番号、履歴不足、並び替え、参加0件。
- サイクルの最古更新選択、同順位、新規参加、失敗時に順序が進まないこと。
- 同一集合・順序違い・アクティブ変更・空選択・ブロック混在の判定。
- 通常履歴と戻る・進むの分岐、期待通知の期限切れ、遅延した通知。
- 明示除外と手動解除が独立し、再ロックで明示除外が消えないこと。
- ランダムな開始・終了・選択・開閉・停止・失敗の列を与え、第4節の不変条件を維持すること。

### 12.2 Fake adapterによる障害注入

各読取・書込・読戻し・復元・保存の境界で失敗させる。特に「3枠中2枠目の更新で失敗」「補償の途中で閉鎖」「ロックは成功したが結果通知前に停止」「購読直後に再読込」「保存領域が読取専用」を検証する。

確認するのは例外の有無だけでなく、実状態と確定状態の一致、Leaseの残存、復旧記録、次のコマンドが実行可能か、自動更新が停止しているかである。

### 12.3 Unity実機での統合検証

| 条件 | 確認内容 |
| --- | --- |
| Unity 2022.3.22f1の標準Inspector | 単一・複数選択、アクティブ対象、異種選択、編集可能性がUnity標準と整合 |
| ドッキング・フローティング・非表示タブ | フォーカスに依存せず割り当てられ、別Inspectorを誤識別しない |
| 標準UI・Manager・ショートカットのロック | 同じ参加状態へ収束し、終了後は開始前ロックへ戻る |
| Prefab編集・シーン切替・削除・Undo/Redo | 参照失効で例外ループや別対象への置換が起きない |
| コンパイル・Assembly reload・Play Mode | 購読が増殖せず、古い計画が実行されない |
| Domain Reload有効・無効 | どちらでも安全停止・復元が行われる |
| Editor再起動・シーン未ロード | お気に入りを保持し、未解決項目を削除しない |
| 内部APIの意図的な能力欠落 | 必要な機能が停止し、履歴・お気に入りを継続できる |

API統合テストの成功だけでは非表示タブやフォーカス依存を検出しきれないため、対話的な実機確認をリリース条件に含める。

## 13. 実装順序と判断ゲート

1. **技術実証**：検証用Inspectorで、グローバルSelectionを変更せずに選択集合を割り当て、読戻し・ロック復元ができるか確認する。非表示タブと再読込をまたぐ識別も検証する。基本能力が成立しなければ、安全な回転を実装できるとは判断せず、対応範囲を見直す。アクティブ対象の厳密な再現は別能力として検証する。
2. **状態モデル**：純粋なReducerとFake adapterを作り、履歴・参加条件・失敗処理を確定する。
3. **実機アダプタとLease**：開始・停止・復元・途中失敗を完成させてから、自動割り当てを接続する。
4. **履歴・サイクル**：成功後確定、フィルタ、停止・再開、並び替えを実装する。
5. **保存とライフサイクル**：お気に入り、破損復旧、再読込、Play Mode、終了処理を実装する。
6. **UIとショートカット**：確定状態の表示と共通コマンドを接続する。
7. **リリース判定**：要件表と実機検証表を満たし、復元できない条件をUIと説明に反映する。

設計上の最優先事項は、正常系の便利さより先に、誰がどのロックを変更し、どの時点で元へ戻すかを確定することである。内部APIの書込みを狭い境界へ封じ、状態遷移と実行結果を分けることで、不確実なUnity操作が機能全体の状態破損へ広がるのを防ぐ。

## 14. 既存実装の調査を反映した実装上の必須条件

本節は初版の抽象設計をUnityに接続するための補足である。既存コードに実装されている対策を根拠とするが、Unity実機での再現確認は今回行っていない。

### 14.1 Inspector操作と成功判定

- `InspectorReflection`が採用するように、表示対象とロックをまとめて設定するウィンドウ側APIを優先する。トラッカー側APIは、別途ロックを立てる必要がある経路として実証する。後者を無条件に同等の能力と判定しない。
- 未生成の`m_Tracker`を読むだけでは初回更新を失敗させうる。既存の`tracker`プロパティ優先取得を引き継ぎ、「準備待ち」と「未対応」を分離する。プロパティ読取がトラッカー生成を伴う点もアダプタの副作用として扱う。
- `activeEditors`にはコンポーネントのEditorも含まれるため、正確な選択集合の読戻しに使わない。既存の`GetObjectsLocked`相当の経路を検証する。先頭Editorの`target`はUIの代表名用に限定する。
- `SetObjectsLocked`、必要な再構築、最適化GUIキャッシュのフラッシュ、`Repaint`を一連の手順として検証する。既存実装のフラッシュ呼出しはstaticであり、インスタンスメソッドとして探索しない。非表示タブでの反映も確認する。
- `Written / Verified / PresentationPending / Failed`を区別する。読戻しが即座に整わない場合は期限付きで次のEditor更新に検証を持ち越し、待機中に新たな書込み計画を始めない。世代変更で失効する。
- 集合とロックの検証能力、アクティブ対象の指定能力、画面反映の能力を分ける。既存の引数は対象リストであり、独立したアクティブ対象指定・読戻しを証明していない。モデルではアクティブを保持しつつ、標準マルチ編集を受け入れ条件とし、厳密なアクティブ再現は実証できた環境のみ保証する。これだけを理由に全回転を使用不能にしない。
- 空のロック対象を「有効な空表示」、失敗を「読取不能」として区別する。空表示を補償で戻せるかも実証する。初版の「全対象を読めれば必ず戻せる」という暗黙の前提を置かず、未対応の枠には書かない。
- 再構築に伴うCustom Editorのコールバック等の任意の副作用は、ロックと表示の補償だけで巻き戻せない。補償の保証範囲はアダプタが所有する状態に限定する。

### 14.2 キャッシュと配置の優先順位

`ForceRebuild`を毎回行わず、対象・アクティブ再現条件・ロック・実体世代が同じで、有効な検証記録がある場合は書込みを省略する。初期キャッシュを現在のSelectionで埋めない。各Inspectorが実際に保持するロック対象から作る。再読込、Play境界、原因不明のロック変更、対象削除、失敗時には失効させる。

復帰時に表示から履歴を再構築する手法は利用できるが、予約済みの明示的なモード変更・並び替えを上書きしない。既存の`_layoutApplyQueued`の意図を、設定リビジョンと処理世代の優先順位で実現する。復旧用の表示観測は新規のSelectionイベントとして記録しない。

### 14.3 UIの実行時点と寿命

単に同一スレッドで直列化するだけでは足りない。コマンドを受けたGUIコールバックから即実行せず、描画処理の外でキューを消化する。IMGUIのLayoutとRepaintで同じスナップショットを使い、行の追加・削除・分岐を描画途中に変更しない。

ウィンドウ一覧は借用した可変バッファを返さない。描画単位で一度だけ取得し、行ごとの再列挙を避ける。ドラッグ操作はWindowKey/FavoriteEntry IDを持ち、実行時に位置を引き直す。対象が消失していれば中止する。

オーバーレイは既存の名前付き要素の重複防止・脱落時の再接続を引き継ぐ。現在のrootとの親子関係も確認し、破棄時にはイベント・生成要素・遅延処理を解除する。成功フラッシュは終了時刻を更新するだけとし、解除コールバックを選択ごとに積まない。Inspector再構築時に表示要素が置き換わっても本体状態には影響させない。

自動フォーカスを提供する場合は既存設定を移行し、Hierarchy/Projectで連続選択している間に入力先を奪わない。ja/en、履歴件数、記録対象、クリーンアップ、ブロックカテゴリの設定を初期化・設定リセットの両経路で一括適用する。

### 14.4 保存・参照解決・移行

通常保存のまとめ書き、未フラッシュ値をLoad/HasKeyへ即反映する性質、再読込・終了・Dispose時のflushを引き継ぐ。復旧記録の先行保存とは別の経路にする。

アセットはGUIDとlocal file IDの組を保持する。解決結果は失敗も含めてキャッシュし、projectChangedやインポート後に失効させる。サブアセットを発見できなかった場合にメインアセットへ代替しない。シーンの一時IDを再起動後の永続識別子としない。

既存のEditorPrefsデータにはプロジェクト識別が付かないため、新しい保存先への移行では現在のプロジェクトで解決できる項目と所属不明の項目を分ける。元データを保持し、不明項目を他の対象へ推測変換しない。初版のセッション内履歴という範囲は維持するが、旧永続履歴は削除せず退避する。自動クリーンアップは未ロード・解決待ちを削除理由にしない。

### 14.5 追加の回帰シナリオ

1. トラッカー未生成のInspectorを追加し、最初の複数選択から正しく表示される。
2. 管理中のトラッカー再生成でロックが落ちても、手動離脱として登録されない。
3. 再読込後の遅延復元とモード変更が交差しても、明示した配置が観測値で巻き戻らない。
4. `A → 空 → A`、戻る操作中の旧値重複通知、期待通知の遅延・欠落で履歴を誤って進めない。
5. タイムアウトした遅延処理が後から到着しても、再ロック・順序変更・成功通知を実行しない。
6. 初回のロック済み表示が現在Selectionと異なっても、キャッシュによって必要な更新を飛ばさない。
7. フォルダとGameObjectの混合選択は集合全体を渡し、`A → B → A`の履歴モードでは表示候補を重複させない。
8. Inspector再構築や連続選択でオーバーレイ・flash・購読・GUIコントロール数が増殖しない。
9. FBXのサブアセット削除、シーン未ロード、旧Instance ID再利用で別対象を選択しない。
10. 設定リセット直後から、履歴上限・記録対象・モード・フィルタ・言語が同じ設定リビジョンを参照する。
